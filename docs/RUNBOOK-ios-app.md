# RUNBOOK: build, archive and upload the iOS app

The Kenworthy iOS app is the website's production build, bundled into a
Capacitor shell (`ios/`, `capacitor.config.ts`). Why it is built the way it is:
`docs/briefs/BRIEF-capacitor-ios-app.md` and `docs/FINDINGS-ios-webview-origin.md`.

| | |
|---|---|
| Bundle id | `org.kenworthy.tickets` (permanent — Apple ids cannot move teams) |
| Display name | Kenworthy |
| Apple account | `tickets@kenworthy.org` (the Kenworthy developer team) |
| Capacitor | 8.5.x, Swift Package Manager (no CocoaPods), UIScene |
| Minimum iOS | 16.0 (Square's Mobile Payments SDK requires it); iPhone and iPad |

## The app does not update itself

The web code is inside the binary. **A website deploy does not change the app.**
Patrons and staff get new code only from a new build through TestFlight or the
App Store. Cut a new build after any production deploy that touches `src/`,
`public/` or `index.html` and matters on a phone.

## Build

From a clean worktree of `origin/main` (CLAUDE.md, "Working in this repo"):

```sh
npm ci
npm run ios:prep
```

`ios:prep` runs, in order, and stops at the first failure:

1. `build:native`: the production build with no service worker, into
   `dist-native/`.
2. `cap sync ios`: copies it into `ios/App/App/public`. Before copying,
   `capacitor:copy:before` runs `scripts/verify-native-bundle.mjs`, which
   refuses a bundle that is not production-only or that carries a service
   worker. It runs on every `cap copy`/`cap sync`, however invoked.
3. `scripts/stamp-ios-build.mjs`: writes the build number to
   `ios/Version.xcconfig` (minutes since 2026-01-01 UTC; gitignored), and the
   Square application id for the Stand (`SQUARE_APPLICATION_ID`), chosen by
   the backend the copied bundle points at: production → Square production,
   staging → Square sandbox.
4. `scripts/verify-native-sync.mjs`: checks the app's copy matches
   `dist-native/` file for file, because `cap sync` can copy nothing and exit 0.

Xcode never runs any of this. **Always `ios:prep` before opening Xcode.** An
un-prepped tree fails to build (missing `Version.xcconfig`) rather than
archiving a stale bundle.

Do not put `# comments` on the same line as these commands at a zsh prompt
without `setopt interactivecomments`; zsh passes them as arguments.

## Versions

- **Marketing version** (`1.0.0`): `MARKETING_VERSION` in
  `ios/App/App.xcodeproj/project.pbxproj`, both configurations. Bump by hand per
  App Store release.
- **Build number:** generated by `ios:prep`. **Never type into Xcode's
  General → Identity → Build field and never run `agvtool`:** both write a
  literal into the pbxproj that silently beats the generated value, and
  `stamp-ios-build.mjs` will then refuse to run until it is put back to
  `"$(inherited)"`.

## Sign in to the team (once per Mac)

Xcode → Settings → Accounts → **+** → Apple ID → `tickets@kenworthy.org`.
Then in the project: target **App** → Signing & Capabilities → Team →
the Kenworthy team, "Automatically manage signing" on. That writes
`DEVELOPMENT_TEAM` into the pbxproj; commit it.

Register the App ID `org.kenworthy.tickets` in the Apple Developer portal if
automatic signing does not create it, and create the app record in App Store
Connect (the API cannot create app records; the web UI can).

## Archive and upload

```sh
npm run ios:prep
open ios/App/App.xcodeproj
```

Product → Destination → Any iOS Device (arm64). Product → Archive. In the
Organizer: Distribute App → App Store Connect → Upload.

Or from the command line, with the Kenworthy account signed in to Xcode
(this is how build 1.0.0 (417221) went up on 17 Oct 2026):

```sh
npm run ios:prep
xcodebuild -project ios/App/App.xcodeproj -scheme App -configuration Release \
  -destination 'generic/platform=iOS' -archivePath /tmp/Kenworthy.xcarchive \
  -allowProvisioningUpdates archive
xcodebuild -exportArchive -archivePath /tmp/Kenworthy.xcarchive \
  -exportPath /tmp/kenworthy-export -exportOptionsPlist ios/ExportOptions.plist \
  -allowProvisioningUpdates
```

`ios/ExportOptions.plist` uploads straight to App Store Connect and leaves the
build number alone (`manageAppVersionAndBuildNumber` false — `ios:prep` owns
it). Automatic signing needs at least one device registered to the team; Tom's
iPhone is.

Before uploading, confirm the archive is what you meant to ship: in the
Organizer, Show in Finder → Show Package Contents →
`Products/Applications/App.app/Info.plist` must carry
`UIApplicationSceneManifest` and `DTSDKName` `iphoneos27.0` (or later). An app
built with the iOS 27 SDK and no scene manifest crashes at launch on iOS 27.

TestFlight builds expire after 90 days.

## Test on the simulator against staging

```sh
npm run build:native:staging
ALLOW_NONPROD_BUILD=1 npx cap sync ios
node scripts/stamp-ios-build.mjs
```

The guard prints a warning and lets the staging bundle through. **Never archive
after this**; run `npm run ios:prep` first, which rebuilds for production.

## The Square Stand (Mobile Payments SDK)

The box-office iPad takes cards through its Square Stand from `/staff/pos`
(`docs/briefs/BRIEF-ios-stand-reader.md`). The SDK is in the app's own plugin,
`native/stand-reader` (a local npm package that `cap sync` adds to
`ios/App/CapApp-SPM`), pinned to an exact SDK version. Square retires old SDK
versions, so check Square's current version before each App Store release and
bump `native/stand-reader/Package.swift` deliberately.

- `AppDelegate` initialises the SDK with `SquareApplicationID` from Info.plist.
- The last build phase runs Square's `setup` script; User Script Sandboxing is
  off for the App target because that script needs it off.
- Info.plist carries the Stand's accessory protocols and the Bluetooth,
  location and microphone usage strings Square requires.
- **App Store submission** needs Square's Stand MFi approval first (Square
  tells Apple the app may use the Stand). Put the protocols and PPIDs Square
  sends back in the review notes. TestFlight internal testing does not wait on
  it.
- Every upload warns "Upload Symbols Failed … did not include a dSYM" for
  `CorePaymentCard`, `LCRCore`, `MockReaderUI`, `SquareMobilePaymentsSDK` and
  `SquareReader`. Square ships these frameworks prebuilt without dSYMs; the
  warning is harmless (Square frames in crash logs stay unsymbolicated) and
  the upload still succeeds.
- If `xcodebuild -exportArchive` fails with "App Store Connect Credentials
  Error … Actor/relationships/providerId" (seen 21 Oct 2026), upload from the
  Organizer instead: `open <archive>` → Distribute App → App Store Connect.
- Production payments need the app's signature registered in Square's
  Developer Console (bundle `org.kenworthy.tickets`, team `26H64FNAKG`).

### Setting up the Stand iPad as the patron-facing display

The usual setup (`docs/briefs/BRIEF-stand-at-patron-display.md`): staff ring
up on any device; the patron chooses a donation and pays on the iPad in the
Stand, outside the glass.

1. On the Stand iPad, in the Kenworthy app: sign in as staff (for now an
   existing staff account; later a dedicated display account). MFA applies.
2. Staff → **Patron-facing display**. The iPad remembers it is the display and
   reopens on it after the app is closed or updated.
3. On the till: Card reader → **Square Stand at the patron-facing display**
   (the default for a new station), then **Pair a patron-facing display**, and
   type the code into the iPad.
4. Once, ever, per environment: an admin taps the **Kenworthy logo** at the
   top of the display to open its staff options, and presses **Connect
   Square**, approving as the Kenworthy Square account in Safari.
5. The till's picker should read **Stand ready**.

The staff options (behind the logo; they close after a minute or when a sale
starts) also have **Sign in as staff** when the app is signed out, Square's
reader settings, **Use a different code**, and **Stop using this iPad as the
display** (the app has no address bar; this is the way out).

If the till says the Stand is "not ready: … not signed in as staff", the app
is sitting on the display signed out (the display page needs no sign-in; the
Stand does). Open the staff options and sign in.

For a special event without a display, the till itself can run on the Stand
iPad: Card reader → **Square Stand (this iPad)**.

## App Store Connect notes

- **App Privacy:** camera (ticket scanner, staff only); contact info and
  purchase history (checkout, via Supabase); payments processed by Square.
- **Export compliance:** `ITSAppUsesNonExemptEncryption` is `false` (HTTPS
  only), so no prompt per build.
- **Review notes:** tickets, passes and donations are real-world goods and
  services paid through Square, which Guideline 3.1.3(e)/3.1.5 permits
  outside In-App Purchase. Provide a staff demo login so review can reach the
  box office and scanner.
- **Screenshots:** iPhone and iPad (the app supports both).
